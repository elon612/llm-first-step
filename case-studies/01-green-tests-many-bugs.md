# 案例 01：测试全绿，Bug 还是很多

> 基于团队笔记《为什么测试全绿，Bug 还是很多——AI 时代的测试分层》和 ai-note-app（Flutter monorepo）的仓库统计展开。
> 本文没有直接访问 ai-note-app 仓库：数据引用自笔记，Dart 代码是**未编译的草图**，类名按笔记里出现的模块虚构。
> 可以直接用的产出是 [templates/fail_first_check.sh](../templates/fail_first_check.sh)，它有测试（`tests/test_fail_first_check.py`）。

## 0. 结论先行

笔记的诊断是对的：bug 住在接缝里，而测试和实现出自同一个上下文，所以测试证明不了任何事。

要补的是三件事：

1. **把“测试是否独立”从纪律变成机器校验**。“严禁同一提交修改实现与测试”这条规则打错了靶子，改成“新测试必须在修复前的代码上失败”（fail-first），由 CI 自动验证。
2. **Oracle（判断对错的标准）要来自现实，而不是来自代码**：真实服务端响应、真实 BLE 抓包、bug 报告里的复现步骤、线上遥测。每条接缝都要写清楚它的 Oracle 从哪来。
3. **移动端要有自己的“生产探测”**。你没法在用户手机上跑探针，但可以让客户端上报“同步队列卡住多久”这类不变量是否被违反。“整队卡死”这类问题，最终要靠它兜底。

## 1. 对原笔记的三处修正

### 1.1 “严禁同提交修改实现与测试”打错了靶子

修 bug 时，把回归测试和修复放在同一个提交里，本来就是好做法。真正的问题不是“同一个提交”，而是**这条测试从来没有被证明能失败**。

这条规则还很容易被机械地绕过：agent 先写好修复，再写测试，然后拆成“测试提交”和“修复提交”两次提交。形式上满足了，Oracle 依然不独立。

替换成一条可以自动验证的规则：

> **修复类改动里新增或修改的测试，放到修复前的代码上必须失败。**

修复前的代码就是一个现成的、真实的“变异体”。这正是笔记里想用变异测试解决、但 Dart 缺工具的那个问题——每个 bug 修复都自带一个免费的变异体。

它是**必要条件，不是充分条件**：能区分修复前后，说明测试至少测到了这次的改动；但它断言的是“用户承诺”还是“实现细节”，仍然要靠第 5 节的流程和 review。

### 1.2 数据口径：先归一化，再下结论

“测试文件涨 10 倍，修复提交不降反升”很有冲击力，但有两个混杂因素：

- **吞吐量**：同期 agent 的使用量上升，总提交量、总改动行数可能也涨了。修复提交数应该除以总提交数或改动行数再比较。
- **分类方式**：“修复类提交”如果按提交信息里的 `fix` 识别，agent 生成的提交信息习惯会直接改变统计结果。

这不影响结论的方向（同一主题反复修 495 次，本身就说明问题），但做第 7 节的度量基线时要用更稳的口径。

### 1.3 缺了“生产 Oracle”

笔记表格最后一行写了“生产主动探测 + Feature Flag 灰度”，但路线图里没有对应的落地项。

后端可以在生产环境跑合成探测；移动端的对应物是**客户端不变量遥测**：客户端自己检查“我是不是处于一个不该出现的状态”，并上报。对“同步队列卡死”“录音文件丢失”这类问题，这是唯一能发现“未知的未知”的层（见 4.6）。

## 2. 用学习路线里的概念重新解释

这个案例几乎把主线课程串了一遍：

| 现象 | 对应概念 | 课 |
| --- | --- | --- |
| 同一个 agent 写实现又写测试，全绿但是坏的 | 测试来自同一个上下文，不是“外部信号”。这是第二课 `--no-verify` 的升级版：不是没跑测试，而是测试本身不独立 | 02、04 |
| agent 倾向于改测试、放宽断言、加 skip 来“保绿” | 模型被训练为“让可验证的检查通过”；当检查就是它自己写的测试时，最省力的路径就是改检查 | 05 |
| mock 返回的是半年前的数据形状 | Oracle 来自代码作者的记忆，而不是现实 | 04 |
| 同一主题反复修 | 缺少评估集：修过的 bug 没有沉淀为可重复跑的任务 | 04 |

第二行是推断，不是定论：它和“RL 用可验证奖励训练 coding 能力”一致，公开研究里也有 agent 为了过测试去修改测试的案例，但具体到你们的仓库，要看 diff 才能确认。

## 3. 目标：每条接缝都写清楚 Oracle 从哪来

| 接缝 | Oracle 来源 | 测试形态 | 反馈时机 |
| --- | --- | --- | --- |
| 同步（DB × 服务端 × 时序） | 真实服务端的版本与冲突语义、历史 bug 的复现步骤 | 真实 drift 内存库 + 行为对齐的 Fake 服务端 + 场景 / 随机操作序列 | MR；夜间对 Staging 复跑 |
| BLE 外设 | 真实设备抓包 | Fake Transport 回放抓包 + 故障注入 | MR |
| 服务端契约 | 录制的真实响应 | DTO 解码测试 + 线上 schema 漂移上报 | MR；线上 |
| 购买状态机 | 产品规则、应用商店的状态文档 | 纯逻辑单测 + 属性测试 | MR |
| 核心用户旅程 | 产品承诺 | 5–10 条 E2E，断言用户承诺 | 夜间 / 发版前 |
| 未知组合 | 线上真实状态 | 客户端不变量遥测 + 灰度 | 线上 |

“行为对齐的 Fake 服务端”是这里最容易出问题的一环：Fake 本身也可能是错的 Oracle。4.1 讲怎么让它保持诚实。

## 4. 各接缝的设计

### 4.1 同步缝（最高优先）

**结构**：只替换进程边界上的东西，进程内全部用真的。

```text
NoteDetailSyncService（真）
   ├── DAO / SyncStore / Cache（真，drift 内存库）
   ├── RemoteDataSource（真，含序列化、拦截器）
   │      └── HTTP client ──→ ScriptedNetwork（假：可编排延迟、失败、乱序）
   │                              └── FakeSyncServer（假：实现服务端的版本号与冲突语义）
   └── Clock（可注入）
```

现在的测试把 DAO、RemoteDataSource、SyncStore、Cache 四道接缝都 mock 掉了。新结构里只剩网络一道是假的，而且假的那一端有自己的状态和语义，不是一行 `when(...).thenReturn(...)`。

**场景测试**（每个近 90 天修过的同步 bug 一条）：

```dart
// 草图，未编译
test('push 遇到 409 冲突后，队列不会卡死，本地修改不会丢', () async {
  final db = AppDatabase(NativeDatabase.memory());
  final server = FakeSyncServer()..seedNote('n1', version: 3, body: 'server');
  final net = ScriptedNetwork(server)
    ..onPush('n1', (_) => Reply.conflict(serverVersion: 4))
    ..latency(const Duration(milliseconds: 300));
  final sync = NoteDetailSyncService(db: db, remote: RemoteDataSource(net.client));

  await db.notes.editLocally('n1', body: 'local', baseVersion: 3);
  await sync.runUntilIdle(timeout: const Duration(seconds: 10));

  expect(await db.syncQueue.pendingCount(), 0);
  expect(server.allVersionsOf('n1').map((v) => v.body), contains('local'));
});
```

断言的是**用户承诺**（队列排空、修改没丢），不是“调用了几次 `push`”。

**不变量 + 随机操作序列**：场景测试只覆盖已知 bug；未知组合用随机生成的操作序列去撞。

```text
随机生成：本地编辑 / 删除 / 离线 / 上线 / 服务端并发修改 / 响应延迟 / 超时 / 409 / 500
随机顺序、随机间隔，执行完后检查不变量：
  1. 队列最终排空，或者进入明确的“需要用户处理”状态，不能无限重试
  2. 不丢写：每一条本地已确认的编辑，最终出现在服务端或冲突副本里
  3. 收敛：两个客户端都同步完成后，内容一致
  4. 版本号单调递增
```

Dart 有 `glados` 这类属性测试库，也可以自己用固定种子的 `Random` 写一个循环。失败时打印种子，把种子固化成一条场景测试。

**让 Fake 服务端保持诚实**：同一套场景测试，夜间用 `SYNC_TARGET=staging` 换成真实 Staging 再跑一遍。两边结果不一致，说明要么 Fake 的语义错了，要么服务端契约变了——两种都是你想尽早知道的。

**迁移**：同步问题常常和 schema 版本有关。drift 自带 schema 导出和迁移测试工具，把“旧版本库升级后再同步”也加进场景。

两个需要实测的点：drift 在 `fake_async` 里能否正常推进（不行就用真实时间，加上可注入的 debounce 间隔）；随机序列每次跑多少轮能控制在 MR 的时间预算内（MR 少跑，夜间多跑）。

### 4.2 BLE 缝

BLE 之于移动端，就像第三方服务之于后端。结构同上：只替换字节进出的那一层。

```text
协议解析 / 通道分发 / 会话状态机（真）
   └── Transport（假：从 test/fixtures/ble/ 读取真实抓包，按帧回放）
             └── 故障注入：分片、乱序、重复、丢包、延迟
```

笔记里提到的三个经典缺陷，各自对应一个不变量：

| 缺陷 | 不变量 |
| --- | --- |
| authSN 串通道 | 帧只会交付给它所属通道的消费者 |
| 文件流字节误认作序列号 | 序列号只从控制帧解析，数据帧里的任何字节都不会改变会话状态 |
| controlSeq 乱序包重组 | 任意乱序 / 重复注入后，重组出的字节流与原始抓包一致 |

抓包文件就是 Oracle，它来自真实设备，不来自写代码的 agent。每次线上出现新的外设问题，第一件事是拿到抓包，放进 fixtures。

### 4.3 契约缝

- **录制**：在 Staging 上跑一遍主要接口，把真实响应存进 `api_contracts/fixtures/`，带上录制日期和服务端版本
- **解码测试**：每个 DTO 用录制的响应解码，断言关键字段的类型和可空性
- **定期重录**：夜间重录一次，与已提交的 fixture 做结构 diff，结构变了就开 issue
- **线上漂移上报**：客户端解码时遇到未知字段、缺失的必填字段、类型不符，按采样率上报（只报字段路径和类型，不报内容）

最后一条就是笔记里说的“盯线上真实响应形状”在移动端的做法。

### 4.4 钱：单测真正该用的地方

购买状态机是纯逻辑，这里单测和属性测试最划算：

- 列出所有状态和事件，每个“状态 × 事件”组合都有明确的期望（包括“忽略”）
- 属性：任意事件序列之后，不会出现“已扣款但未发放权益”的状态；恢复购买是幂等的

这也是在回答“要不要扔掉单测”：不扔，放回它擅长的地方。

### 4.5 E2E：少而准

- 只保留 5–10 条核心旅程：登录、新建笔记并同步到第二台设备、录音并完成转写、购买并获得权益、离线编辑后上线恢复
- 断言用户承诺：“第二台设备在 60 秒内看到内容”，而不是“某个 widget 可见”
- 需要系统弹窗（权限、蓝牙配对）时，用能操作原生界面的框架（如 Patrol），或者放到真机上手动冒烟
- BLE 相关的 E2E 只在真机设备池上跑一两条冒烟，主要防线在 4.2

### 4.6 生产 Oracle：客户端不变量遥测

在客户端埋这些检查，违反时上报（带版本、设备型号、功能开关状态）：

| 不变量 | 上报条件 |
| --- | --- |
| 同步队列在推进 | 最早的待同步项超过 N 分钟没有被处理 |
| 冲突能被处理 | 同一条目连续冲突超过 K 次 |
| 录音可恢复 | 录音会话结束后找不到对应的音频文件 |
| 外设会话健康 | 一次会话内重连超过 K 次，或出现未知帧类型 |

配合灰度：新版本先放给小比例用户，看这些指标，再全量。

每一条上报背后都应该有一个问题：**这类情况能不能在 4.1–4.3 里复现？** 能复现的，就变成一条回放场景。这就形成了闭环：线上 → 回放测试 → 永久防线。

## 5. Agent 工作流：让 Oracle 独立

核心是把“写测试”和“写修复”放进**不同的上下文**。

```text
阶段 1：复现（repro agent，或者人）
  输入：issue、日志、抓包、用户复现步骤      ← 不给它看修复思路
  输出：test/regression/<主题>/ 下一条失败的测试
  检查：CI 证明它在当前 main 上是红的

阶段 2：修复（fix agent）
  输入：issue + 那条失败的测试
  约束：不许修改阶段 1 的测试文件
  检查：fail-first 校验通过；全部测试通过

阶段 3：review（人）
  只看一件事：阶段 1 的测试断言的，是不是 issue 里用户说的那件事
```

在 Cursor / Claude Code 里，阶段 1 和阶段 2 可以用两次独立的对话，或者一个子 agent 来做——关键是修复的推理过程不能出现在写测试的上下文里（第三课“子 agent 隔离上下文”的同一个道理）。

**建议的 AGENTS.md 测试纪律（替换原来的六条）**：

```markdown
## 测试纪律

- 修 bug：先在 test/regression/<主题>/ 写一条失败的测试，断言用户可观察的结果，
  确认它在修复前失败，再改实现。
- 不许为了让测试通过而修改、跳过或放宽已有的断言。测试和需求冲突时，停下来说明。
- 同步、BLE、网络、数据库这些接缝上，不要 mock 进程内的类：用 drift 内存库、
  Fake Transport、ScriptedNetwork。
- 断言结果，不断言过程：不要断言“某个方法被调用了几次”，除非这就是需求。
- 不许使用 `--no-verify` 跳过本地钩子。
- 不改行为的重构，在提交信息里写 `Fail-First: skip <理由>`。
```

**受保护的回归测试**：`test/regression/` 配 CODEOWNERS，修改已有文件需要指定的人审批。新增文件不受限。这样 agent 可以随便加测试，但不能悄悄改掉证明 bug 存在的那条。

## 6. 门禁 v2：按速度分层

笔记里的 TODO 问“pre-commit 跑改动包测试的成本能不能接受”。建议：**不在 pre-commit 跑测试**。

原因：pre-commit 一慢，人会加 `--no-verify`，agent 也会。本地钩子只能当提醒，真正的门禁在 CI。

| 层 | 跑什么 | 时间预算 |
| --- | --- | --- |
| pre-commit | skip / only 标记拦截、改动文件的 `dart format` 与 `flutter analyze` | 10 秒内 |
| pre-push | 改动包的测试（现有 `test_discipline_gate.sh` 的测试部分） | 2–3 分钟 |
| MR 流水线 | 全部受影响包的测试；`fail_first_check.sh`；测试净删除告警；`test/regression/` 的 CODEOWNERS | 15 分钟内 |
| 夜间 | 同步场景对 Staging 复跑；随机序列多跑轮数；契约重录 diff；真机 E2E | 不限 |

`fail_first_check.sh` 的 Flutter 接入：

```bash
# GitLab MR 阶段
bash templates/fail_first_check.sh "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
```

它会在修复前的代码上开一个 git worktree，把分支里改过的 `test/`、`integration_test/` 文件（包括 fixture）拷过去，逐个运行改过的测试，按最近的 `pubspec.yaml` 选择 `flutter test` 或 `dart test`。有测试在旧代码上通过就判失败。

已知局限：

- 新功能的测试在旧代码上常常是**编译失败**，脚本也会算作“失败”。这对新功能来说没问题，但它证明不了太多——fail-first 主要对修复类改动有意义
- monorepo 里每个包都要 `pub get`，CI 上要缓存 pub 目录，否则会慢
- 先在 MR 上**只告警不拦截**跑两周，看误报率，再改成硬门禁

## 7. 度量：怎么知道这套东西有用

按第四课的思路：先有基线，同一口径，定期对比。

| 指标 | 定义 | 为什么 |
| --- | --- | --- |
| 逃逸缺陷数（按主题） | 合入 main 之后才被发现的缺陷：QA、内测、线上 | 这才是“测试拦没拦住”的直接度量 |
| 90 天复发率（按主题） | 同一主题 90 天内再次修复的比例 | 直接对应“录音 495 次” |
| 发现位置分布 | CI / QA / 线上各占多少 | 防线前移了没有 |
| fail-first 覆盖率 | 修复类 MR 中，带通过 fail-first 校验的测试的比例 | 纪律有没有落地 |
| 修复提交占比（归一化） | 修复提交数 / 总提交数 | 修正 1.2 的口径问题 |
| flaky 率 | 同一 commit 重跑结果不一致的测试比例 | 集成测试变多之后最大的风险 |

## 8. 路线图（在原来四步上加了退出标准）

| 步 | 内容 | 退出标准 |
| --- | --- | --- |
| 0 | 度量基线；`fail_first_check.sh` 以告警模式上 MR；AGENTS.md 换成第 5 节的纪律；客户端埋同步队列卡住的遥测 | 有近 9 个月按主题的逃逸 / 复发基线；遥测上线 |
| 1 | 同步缝：4.1 的测试框架；近 90 天的同步 bug 全部变成场景；随机序列 + 不变量 | 同步主题的复发率连续两个月下降；夜间对 Staging 复跑稳定 |
| 2 | BLE 缝：Fake Transport + 抓包回放 + 故障注入；三个经典缺陷回放 | 新的外设问题在 QA 前被 CI 拦住的比例上升 |
| 3 | 契约 + 钱：录制 fixture、解码测试、线上漂移上报；购买状态机的单测和属性测试 | 服务端字段变更在合入前被发现 |
| 4 | E2E 收敛到 5–10 条；富文本 WebView 集成测试；fail-first 改为硬门禁 | E2E flaky 率低于约定阈值 |

原笔记里“明确不做”的三项保留。再加一项：**不做一刀切禁止 mock**。领域层、纯逻辑里的 mock 没问题；限制的是接缝上的 mock。

## 9. 风险

| 风险 | 对策 |
| --- | --- |
| 集成测试变慢、变 flaky，大家开始跳过 | 按第 6 节分层；flaky 测试进隔离区并限期修复，不许直接删 |
| Fake 服务端 / Fake Transport 本身写错了 | 夜间对 Staging 复跑；BLE 只用真实抓包，不手写字节 |
| agent 学会绕过门禁 | 门禁在 CI，不在本地；`test/regression/` 受 CODEOWNERS 保护；review 只盯断言 |
| fail-first 被豁免滥用 | 统计 `Fail-First: skip` 的使用率，高于某个比例就复盘 |
| 遥测涉及隐私 | 只报状态、计数和字段路径，不报内容 |

## 10. 对笔记里三个 TODO 的建议

**“AI 写的测试默认不可信”这条怎么判断？**
不是“默认不可信”，而是“默认未经证明”。一条测试的可信度，取决于它的 Oracle 从哪来（现实 vs 代码作者），以及它有没有被证明能失败（fail-first）。人写的测试如果是先写代码再补的，也一样未经证明。所以规则不该针对“AI”，而应该针对“Oracle 的来源”和“是否证明过能失败”。

**项目里 bug 最密的缝是哪一条？**
按笔记的数据，是**同步缝和它的时序**：同步 193 次、离线 144 次，而且录音（495 次）的很多问题很可能也落在“录音文件 × 上传 × 同步”的交叉点上。建议把录音相关的修复提交按改动文件归类一次，确认有多少碰到了同步和存储层。如果比例高，第 1 步的收益会比预期还大。

**pre-commit 跑改动包测试的成本能不能接受？**
见第 6 节：不建议。pre-commit 只做 10 秒内能完成的检查，测试放到 pre-push 和 MR。
