# 07. 分支：App 本身要加 AI 功能

前六课讲的是“用 agent 写代码”。这一课讲的是另一件事：**你写的 App 要调用 LLM**。

角色变了：之前你是 agent 的用户，现在你是 harness 的作者。第二课的循环、第三课的上下文、第四课的评估，都要自己来做。

只在有这类需求时学这一课。

## 第一个决定：云端还是端侧

| | 云端 API | 端侧模型 |
| --- | --- | --- |
| 能力 | 强 | 弱（通常几十亿参数以内） |
| 成本 | 按 token 付费 | 免费，但占包体积和内存 |
| 隐私 | 数据出设备 | 数据不出设备 |
| 离线 | 不能 | 能 |
| 延迟 | 受网络影响 | 受设备性能影响 |

端侧入口：

- iOS：Apple Foundation Models 框架
- Android：Gemini Nano（ML Kit GenAI API）
- 跨平台 / 自带模型：MediaPipe LLM Inference、llama.cpp
- Flutter：通过 platform channel 调用上面的原生 API，或者找封装好的插件

端侧模型能不能装进手机，由**量化**决定（第六课）：一个 30 亿参数的模型，16 位约 6GB，4 位约 1.5–2GB。

## 应用层必须处理的四件事

1. **流式输出**：逐 token 显示，不然用户要盯着空白等几秒。Flutter 里就是一个 `Stream<String>`
2. **结构化输出**：要 App 能解析的结果，就用 JSON schema 约束输出，别用正则去抠自然语言
3. **失败兜底**：超时、限流、输出不合 schema、内容审核拒答，每种都要有 UI 状态
4. **成本控制**：限制上下文长度、缓存结果、便宜模型优先

## RAG：什么时候需要

模型不知道你们的业务知识（商品、帮助文档、用户数据）时，把相关内容检索出来拼进 prompt。

```text
用户问题 → 检索（关键词 BM25 / 向量 embedding / 两者混合）→ 取前几段 → 拼进 prompt → 模型回答
```

要记住的只有一句：**检索进来的文档，只是被拼进 prompt 的额外 token**。回答质量的上限，由拼进去的内容对不对决定。

效果不好时，按这个顺序查：

1. 切块：文档切得太碎或太大，答案被切断了？
2. 召回：正确的段落有没有被检索出来？
3. 使用：检索到了，模型有没有用上？

coding agent 很少用这种 RAG，因为代码可以直接 grep；但产品文档、客服知识库这类非结构化内容正适合它。

## 评估

第四课的方法原样适用：收集真实用户问题，写通过标准，每次改 prompt、换模型都在同一批问题上跑。
上线后，把用户点了“没帮助”的对话加进评估集。

## 这一课结束的标准

- 能为一个具体功能说清选云端还是端侧，以及理由
- 做过一个最小 RAG，并定位过一次失败发生在切块、召回、使用中的哪一步
- App 里的 LLM 调用有流式输出、结构化输出和失败兜底
