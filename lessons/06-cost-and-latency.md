# 06. 成本与延迟：看懂账单和速度

你在用量页面看到的数字，可以用三件事解释：**输入 token、输出 token、缓存**。

## agent 的钱花在哪

第二课的 `~tokens` 列已经展示了：每一轮，**整段 messages 都要重新作为输入发给模型**。

```text
第 1 轮输入：system + 工具列表 + 任务
第 2 轮输入：上面全部 + 第 1 轮回复 + 工具结果
第 3 轮输入：上面全部 + 第 2 轮回复 + 工具结果
...
```

所以一次 20 轮的 agent 任务，总输入 token 大约是“最终上下文长度 × 轮数 / 2”，远大于你看到的对话长度。

| 花费来源 | 特点 |
| --- | --- |
| 输入 token | 量最大；读大文件、贴长日志、长对话都在涨 |
| 输出 token | 单价通常是输入的数倍；整文件重写比精确编辑贵得多 |
| reasoning token | 按输出计费，你看不到全部内容，但要付钱 |

## 为什么首 token 慢、后面快

- **Prefill**：先把整段输入一次性算完。输入越长，等第一个字越久
- **Decode**：之后每次只算一个新 token
- **KV Cache**：prefill 算过的中间结果被缓存，decode 时不用重算前文

所以上下文很长时，agent 每一轮“开始动”之前都会顿一下。

## Prompt caching：rules 为什么要稳定

服务商会缓存**前缀完全相同**的输入，命中缓存的部分通常便宜很多、也更快。

```text
[system][工具列表][AGENTS.md][历史...][本轮新内容]
 └────────── 每轮都一样，能命中缓存 ──────────┘
```

推论：

- rules、工具列表放在最前面，并且保持稳定
- 对话中途改 rules、增删 MCP 工具，会让后面的缓存失效
- 同一个任务在一段对话里连续做完，比频繁切换更省（但太长又会 context rot，要平衡）

## 模型怎么选

| 任务 | 选择 |
| --- | --- |
| 规划、疑难排查 | 最强的模型，必要时开 reasoning |
| 按计划执行的机械修改 | 更快更便宜的模型 |
| 大量搜索、读代码 | 交给子 agent，别让它塞满主上下文 |

## 量化：一句话

把权重从 16 位降到 8 位或 4 位，体积和内存减半甚至更多，质量略降。
对你来说主要在第七课（端侧模型）用得上；云端 API 的量化是服务商的事。

## 这一课结束的标准

- 能解释一次 agent 任务的输入 token 为什么远大于对话长度
- 能说出 prompt cache 命中的条件，以及哪些操作会让它失效
- 看一次自己的真实用量，估算一个典型任务的花费
